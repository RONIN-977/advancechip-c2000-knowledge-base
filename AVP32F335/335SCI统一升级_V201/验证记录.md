## SCI 只回复 0xCC 修正（2026-09-29）

用户实板反馈：30.000 MHz BOOT 已运行闪灯，115200/8N1 下发送版本请求 `CC 58 00 E9 01 01 00 01 00 2A CA`，只收到 `CC`。原发送启动顺序先写 SCITXBUF，后开启 TXINTENA。非 FIFO 模式下，首次及重新开启发送中断时，必须先开启 TXINTENA 再写 SCITXBUF 才产生首个 TX 中断；原代码只发出手动写入的首字节，其余字节停在缓冲区。[SCI 手册 SCICTL2 说明](https://www.ti.com/lit/ug/sprui07/sprui07.pdf#page=604) 与本次用户现象、代码和回归结果相符。

已仅调整这两项寄存器操作的先后顺序，公共源码与 30m/33.3m 的 BOOT/APP 四套独立工程均同步；协议、BOOT 标识 201、晶振配置和 115200/8N1 不变。所有交付 OUT/MAP 已重新生成，上位机两个固件目录同步更新。

新增 `tests/run-sci-runtime-tests.py`：编译实际 RX/TX ISR 和主循环 C 代码，采用文档规定的非 FIFO 发送中断触发模型。反向恢复旧顺序可复现仅 CC；修正后版本应答 37 字节（含 BOOT 201、CRC）、后续请求、重复应答、状态应答、坏 CRC 拒绝及接收恢复通过。既有 7 组协议/MD5/Flash 桩测试重新通过，四套原生 C2000 编译和 CCS 完整构建通过，MAP/COFF 分区检查通过。八个新 OUT（交付及 CCS 各四个）的反汇编确认先使能 TXINTENA、再写 SCITXBUF；证据见 `sci-runtime-tests.json` 和 `sci-tx-disassembly.txt`。

这些是软件与构建验证。仅 CC 是用户提供的修正前实板证据；修正后实板完整应答、擦写与启动尚待用户复测。请重新通过 JTAG 烧入本次新的对应晶振 BOOT，复位后读版本，再使用本次新的 APP OUT 升级。原发送缺陷不会因只更换 PC 上位机而修复。

## 0x70 错误码 1：CSM 初始化判断修正（2026-09-29）

用户确认 SCI 修正后可以进入升级模式并读取 BOOT 201；随后开始升级命令 0x70 返回错误码 1。核查发现 `Library/src/AVP33x_SysCtrl.c` 的 `CsmUnlock()` 返回 1 表示成功、0 表示失败；而 `Main/AVP33x_API_Library.h` 中 Flash API 的 `STATUS_SUCCESS` 为 0。原 `InitFlashAPI()` 混用了返回值约定，正常解锁会使 `apiReady=0`，在调用 Flash 擦除前被 `beginUpdate()` 拒绝。

主工程及两套独立 BOOT 的 `HardwareSetup.c` 已改为 `RemoteModbus.apiReady = (Status == 1U)`，保留 Flash 擦写函数原有的成功码 0。只需重烧本次新的对应晶振 BOOT；APP 和上位机程序无需替换，当前 5650 字节 APP 可继续使用。BOOT 标识仍为 201，因此用文件更新和 SHA256 区分本次构建。

原测试直接把 apiReady 设为 1，漏测了初始化路径。现已让全部协议测试先执行从工程提取的实际 `InitFlashAPI()`，以 CSM/Flash 桩模拟成功和失败。修正前新增测试失败；修正后解锁成功进入 0x70 擦除、解锁失败不调用擦除均通过，全部 8 组 C 回归通过。原生 C2000 编译、CCS 完整构建、MAP/COFF 校验通过；交付和 CCS 的两套 BOOT 反汇编均确认按返回值 1 判断成功。证据见 `SCI验证/csm-init-tests.json`、`csm-init-disassembly.txt`、`firmware-tests.log`。

实板边界：用户已验证通信、进入升级及版本读取；本次 CSM 判断修正后的完整擦除、写入、MD5 和复位启动仍待用户复测。
