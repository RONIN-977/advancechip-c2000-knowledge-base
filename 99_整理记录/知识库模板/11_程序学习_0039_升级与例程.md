# AVP32F0039：在线升级与例程

更新时间：2026-09-23。静态学习 [0039CAN Bootloader 资料包](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader>)、[AVP32F0039_Examples](<../AVP32F0039/AVP32F0039_Examples/AVP32F0039_Examples/examples>) 与 [Flash API 操作文档](<../AVP32F0039/05_烧录与开发说明/AVP32F0039FlashAPI操作文档.docx>)；没有 CCS 重新编译或实板升级。用户确认 0039 已量产、实际按 120 MHz 配置。这里的 `demo_v1`、`demo_v2` 是**升级工程与协议版本**，不能混当芯片版本。

## 升级工程：按版本成套使用

| 工程组 | 实际接口、协议与入口 | 分区 |
|---|---|---|
| V1 CAN | [BOOT](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/0039bootloader/AVP32F0039_BOOT_CAN_ADV>)、[APP](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/0039bootloader/AVP32F0039_APP_CAN_ADV>)；CAN-A 的 GPIO12/RX、GPIO13/TX，500 kbit/s，标准帧上位机请求 `0x7A0`、芯片应答 `0x7B0`。协议含会话 `0x10`、授权 `0x27`、状态 `0x31`、擦除 `0x34`、写包 `0x36`、CRC/退出 `0x37`、复位 `0x11`，见 [V1 协议源码](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/0039bootloader/AVP32F0039_BOOT_CAN_ADV/UserCode/Com/Src/CAN_upgrade_protocol.c>)。 | BOOT SEC0–2，APP SEC3–14、入口 `0x083000`，SEC15 用作 EEPROM。 |
| V1 UART | [BOOT](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/demo_v1/AVP32F0039_BOOT_UART>)、[APP](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/demo_v1/AVP32F0039_APP_UART>)；SCIA GPIO28/RX、GPIO29/TX，115200 8N1。串口帧为 `FF FF + 类型 + 8 字节载荷 + 8 位累加和 + 0A`；载荷转给同一 V1 升级协议处理入口，见 [串口封装](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/demo_v1/AVP32F0039_BOOT_UART/UserCode/Com/Src/uart_transfer_protocol.c>)。 | 与 V1 CAN 相同：APP `0x083000`。 |
| V2 CANFD | [BOOT](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/demo_v2/AVP32F0039_BOOT_CANFD_V20>)、[APP](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/demo_v2/AVP32F0039_APP_CANFD_V20>)；MCAN GPIO4/TX、GPIO5/RX，标称 500 kbit/s、数据相 2 Mbit/s。V2 采用 `0x55AA` 包头、包长度、序号、功能/子功能 ID、数据段和 16 位累加和，再用 CANFD 单帧/首帧/续帧承载。功能 0x01 查询、0x02 固件操作、0x03 控制；固件操作包含擦扇区、128 字节分包写、CRC 校验、写校验/长度和容量检查。见 [V2 协议表](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/上位机V2/V2在线升级协议.xlsx>)、[协议源码](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/demo_v2/AVP32F0039_BOOT_CANFD_V20/UserCode/Com/Src/CAN_upgrade_protocol.c>)。 | BOOT SEC0–3，APP SEC4–14、入口 `0x084000`，SEC15 用作 EEPROM。 |

V1 与 V2 的 BOOT/APP、链接脚本和上位机协议必须各自配套；V2 比 V1 多占一个 BOOT 扇区，V1 APP 若与 V2 BOOT 混用会落入错误入口或擦写范围。三套工程均以固定 RAM 地址 `0x009FFE` 传递 APP 请求升级/BOOT 返回 APP 的标志；BOOT 启动时按 APP 长度、末尾 CRC16 校验，通过后才跳 APP，升级时调用 Flash API 擦、编程并校验。V1 以 128 字节包转 64 个 16 位 word，分 8 次写入并逐次校验；V2 使用 128 字节分包及独立的传输包累加和、整包 CRC16。V1/V2 的 APP 长度与 CRC 位于 `0x08EFF8` 附近。见 [V1 写入与启动判断](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/0039bootloader/AVP32F0039_BOOT_CAN_ADV/UserCode/Com/Src/dsp_program.c>)、[V2 写入与启动判断](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/demo_v2/AVP32F0039_BOOT_CANFD_V20/UserCode/Com/Src/dsp_program.c>)和各自 `28003x_generic_flash_lnk.cmd`。

[上位机 V2 使用说明](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/上位机V2/AdvchipTool使用说明.docx>)明确要求按测试工程选择 `v1.0`、`v2.0` 或其他协议；它的 LIN 选项写的是 `uds_on_lin_036`，**不能当作 0039 已有 LIN BOOT/APP 工程**。本批 0039 源码找到 CAN、UART、CANFD 三种升级工程，没有找到 0039 的 LIN 升级 MCU 工程。例程中的 SCI/CAN Flash Kernel 是另一种引导烧录参考，不能自动等同于这套驻留 Flash 的 BOOT/APP 产品升级方案。

## 使用前必须核对的源码与配置

1. 三套 BOOT 均选择外部晶振并配置到 **120 MHz**：V1 CAN、V2 CANFD 用 10 MHz 晶振、`REFDIV=1`；V1 UART BOOT 用 20 MHz 晶振、`REFDIV=2`；均为 `IMULT=48`、`ODIV=4`。更要注意，同一套 **V1 UART APP** 却按 10 MHz 晶振、`REFDIV=1` 配置，和其 BOOT 不一致；APP 也会执行 `Device_init()`，在 20 MHz 板上原样使用将使目标时钟配置翻倍，**须先统一整套 BOOT/APP 与实际晶振**。部分 `dsp_base.c` 注释写“外部 20 MHz”，不能代替有效宏。Flash 等待配置为 5，与 0039 Flash API 文档的 120 MHz 示例一致。
2. V1 CAN **APP** 的 `DEVICE_SETCLOCK_CFG` 使用 10 MHz 晶振、`REFDIV=1`，实际配置 120 MHz，但其 [device.h](<../AVP32F0039/0039CAN  Bootloader/0039CAN  Bootloader/0039bootloader/AVP32F0039_APP_CAN_ADV/Library/device/include/device.h>) 的 `DEVICE_SYSCLK_FREQ` 却按 `REFDIV=2` 算出 **60 MHz**。APP 的 `CAN_setBitRate()` 和定时器均使用这个宏；若原样编译，时基/波特率可能错误，必须先统一宏与 PLL 配置并重新验证。
3. 三套 BOOT 的 `Flash_API_Init()` 都调用 `Fapi_initializeAPI(F021_CPU0_BASE_ADDRESS, 100)`；同库 [Flash API 示例](<../AVP32F0039/AVP32F0039_Examples/AVP32F0039_Examples/examples/flash/flashapi_ex1_programming/source/flashapi_ex1_programming.c>)用 `DEVICE_SYSCLK_FREQ/1000000U`，并说明该参数为运行频率 MHz。**120 MHz 配置与参数 100 不一致**；移植或投产前需按当前进芯 Flash API 文档/库说明确认并在实机验证，不能仅凭已有 `.out` 判定正确。
4. V2 BOOT 和 APP 的 `dsp_info.info.app_tail_address` 仍写 `0x3F1FFD`，这是 035 类旧地址；0039 V2 链接脚本的 APP 末段在 `0x08EFF8–0x08EFFF`。V2 `0x01/0x0B` 查询服务会把这个字段返回上位机，属于明确的错误地址字段，复用前应纠正并确认上位机是否使用它。
5. V2 `Receive_Data_Unpack()` 对 `0x55AA` 包头判断的两个分支都不拒绝数据；续帧序号不匹配的分支也继续收包，固定长度缓冲的收包边界没有完整防护。固件长度检查是单独子命令 `0x02/0x0A`，写包 `0x02/0x07` 本身未见 APP 区累计地址上限拦截。正常上位机流程可能规避这些情况，但把工程用于现场升级前仍需验证异常帧、重传和越界路径。
6. V2 的 `0x02/0x02`、`0x02/0x03` 临时区/备份区分支目前只回固定数据，没有对应双分区写入实现；不能据此宣传 A/B 回滚能力。V2 `app_verify_type=1` 时 BOOT 检查整包 CRC 后跳 APP，不能把“返回写入成功”误作最终固件有效性验证。

## 例程：按外设用途查，而不是逐个驱动库文件计数

`AVP32F0039_Examples/examples` 下有 **327 个 CCS `.project`**，分布于 ADC、AES、BGCRC、CAN、MCAN、LIN、SCI、Flash、ePWM、HRPWM、CMPSS、CLB、FSI、GPIO、DMA、DCSM、看门狗等 44 类目录。它们多采用 `Device_init()`/`Board_init()` 和 DriverLib；`device.h` 默认宏为 120 MHz、Flash 等待 5。数量说明资料包覆盖面，不代表 327 个项目均已在当前进芯出货芯片上逐项验证。本轮抽查的代码导航：

| 类别 | 代表例程与可学内容 |
|---|---|
| ADC / PWM | [ADC 软件触发 SOC](<../AVP32F0039/AVP32F0039_Examples/AVP32F0039_Examples/examples/adc/adc_ex1_soc_software/source/adc_ex1_soc_software.c>)、[ePWM 对称计数/AQ](<../AVP32F0039/AVP32F0039_Examples/AVP32F0039_Examples/examples/epwm/epwm_ex2_updown_aq/source/epwm_ex2_updown_aq.c>)。前者展示采样/中断路径，后者用 ePWM1–3 比较值与 ISR 调波形；与客户功率板连接需另核。 |
