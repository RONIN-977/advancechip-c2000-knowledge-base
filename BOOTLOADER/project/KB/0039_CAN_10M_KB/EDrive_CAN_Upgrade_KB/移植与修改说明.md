# 移植与修改说明

## 一、客户侧调用只有一处

`APP_KB/01_main/main.c`：新增 `#include "kb_can_upgrade.h"`，在原 `while(1)` 的第一句新增：

```c
KB_CAN_UpgradeTask();
```

不需要另加初始化调用，第一次调用会初始化升级邮箱和Timer2。必须放在客户系统、CAN和邮箱初始化之后；后续在后台尽可能频繁调用。不要搬到ISR，不要在ISR重入，也不要每个周期再次初始化CAN。原main去掉新增头/调用后与用户 //123 原文件逐字节一致。

## 三、为什么不会重新覆盖客户CAN

客户 `01_main/02_can/canConfig.c/h` 未改。`init_eCAN_A(20,5,4,1,2,1)`、位时序寄存器计算和写入流程未改，100MHz下继续500k。客户调试/普通模式原TX对象与RX10～16保留；升级只使用31/32，消息ID0x601/0x581不和当前客户报文表重叠。

升级函数不调用CAN_initModule、不重设波特率、不清除其他对象。初始化前检查31/32是否已占用，有占用便拒绝新增。升级邮箱未使能CAN接收中断，始终由该函数轮询。客户RX遍历范围保持10～16，不会读取31。

IF2读帧和随后的DLC读取放在同一短临界区；IF1发送寄存器装载也有短临界区，保留进入前中断状态。总线发送等待通过后续主循环调用推进，不在500ms等待中持续关中断。

恢复客户完整代码后，客户ISR仍不能读取/清除31、重配32，也不能再次初始化整个CAN。若新增另一条使用IF1/IF2的可嵌套ISR，仍须协调其自身并发。邮箱单深度，客户算法/中断恢复后必须实测后台轮询间隔和总线负载；不能凭本模型保证满负载下不丢帧。

## 五、003x支持与时钟

003x bitfield头/源/寄存器CMD及driverlib整套取自知识库0039 demo_v2的Library，未把002x寄存器结构改名冒充003x。系统初始化使用 `InitSysPll(XTAL_OSC,IMULT_40,REFDIV_1,ODIV_4,PLLCLK_BY_1,...)`；device.h同时10MHz×40/4=100MHz；examples.h CPU_RATE=10.000ns。Timer1原0.5ms计算仍为100×500，Timer0/1原分频不变。

该003x支持源的SPI分频原只支持120MHz，已增加100MHz对应分支，维持示例500k SPI换算；该函数不在当前客户初始化流程中调用。globalprototypes.h的IDLE声明加已有宏保护，兼容driverlib先被客户CAN头包含的情况。Flash等待保持5，flash_hal_init不会再降回4。

BOOT vendor/device、源代码和120MHz时钟保持原哈希；只更新本地分区头、引脚映射、工程名及说明注释。

## 六、Flash/RAM布局

地址均为C28x 16位字地址。

| 地址范围 | 用途 |
|---|---|
| 0x080000～0x080001 | BOOT codestart |
| 0x080002～0x083FFF | BOOT代码/Flash API加载区 |
| 0x084000～0x084FFF | BOOT有效镜像元数据 |
| 0x085000～0x085FFF | 客户原config保留 |
| 0x086000～0x086FFF | 客户原NVM保留 |
| 0x087000～0x0AEFFF | APP可升级区，结束边界0x0AF000不包含 |
| 0x0003F8～0x0003FB | APP写入、BOOT启动消费的4WORD请求标记 |

新APP的CMD来自APP_KB布局，使用统一APP_FLASH区域，不再沿用客户的碎片链接布局；003x寄存器CMD提供真实硬件地址。两工程普通RAM都不分配M0，因此请求标记不落入bss/栈。Flash API和客户.TI.ramfunc统一以RAMLS运行，加载/运行范围符号配齐。BOOT擦APP从0x087000开始，元数据单独擦0x084000，不擦客户0x085000/0x086000。

新分区与旧BOOT的0x090000入口不一致，必须烧录本文件夹的配套BOOT。本次不要求移动客户现有config/NVM地址，但新CMD其余布局整体替换。

## 七、以后客户恢复全部代码时

1. 恢复 //123 及缺失模块，需要客户提供真实模块，不能直接把注释全部取消就认为编译完整。
2. 保留while中的KB_CAN_UpgradeTask调用；不要重复调用升级初始化，不要再次初始化/重配置Timer2。Timer0/1继续客户使用。
3. 恢复三个原ISR并核对清标志/溢出/PIE ACK后，搜索KB_UPGRADE_TEST_IRQ，把对应PIE位恢复为1；不能只开中断却没有handler。
4. 保留31/32为升级专用。客户若扩展邮箱，先修改升级分配并同步相关配置，初始化占用检查只防覆盖，不能代替完整设计核对。
5. 现场维持12/13。30/31只用于用户开发板测试，客户GPIO30原FO故障输入定义没有删除，恢复控制算法后不能把它同时用作CAN RX。
6. 成功ACK后调用Customer_ShutdownForUpgrade()，默认实现按用户要求留空，不再硬编码PWM/GPIO停机。客户在kb_customer_shutdown.c中实现实际停机和禁止重新启动，确认完成后返回；升级任务随后关中断、写RAM标记、约20ms持续喂狗并复位。回调进入时保留原中断状态，可使用客户已有停机流程；如回调等待较久，需要自行管理喂狗。空回调本身不提供设备停机功能。
7. 原 //123 的PWM4周期/比较值仍处于屏蔽状态，电机相关任务也没有恢复。当前目标是测试升级入口，不能用该工程直接运行电机。
8. 客户后续真实Flash/NVM写操作和ISR的执行位置、Flash API调用链仍需单独运行验证，本次只验证进入BOOT，未验证客户参数保存业务。

本次软件模型不执行真实C28x指令或并发ISR。完整工程恢复后的资源、轮询负载和硬件停机状态需要客户完整源码和实板确认。

## 空停机回调修改与影响范围复核（2026-10-19）

硬编码ePWM1～3 Trip配置/强制停机语句已经删除。Customer_ShutdownForUpgrade()单独放在kb_customer_shutdown.c，当前函数体只有TODO注释；客户可直接填写，不需要再修改升级Task。调用顺序是：完整应答发送完成 → 客户停机回调 → 关中断 → 写RAM标记 → 喂狗延时 → 复位。回调期间升级任务不额外改变原INTM；客户应在真实设备停机并禁止再启动后返回，等待期间自行管理喂狗。

已核对现有客户CAN邮箱/ID/位时序表不变，主循环除单一升级调用外保持原文。不能把这解释为“所有客户代码恢复后零影响”：升级专用Timer2和邮箱31/32不得重用；当前//123测试版关闭的三条PIE通道，恢复原ISR后必须同步恢复；003x支持/CMD替换、满负载中断和控制任务都需要客户完整源码及实板验证。空回调不会主动关机，客户实现前不应据此认定真实设备已具备升级前停机保护。

上位机必须选择APP起始字地址0x087000。本次核对到的桌面上位机有该输入框；填写后再选择新OUT，开始升级会调用进入BOOT再进行下载。默认0x090000会在固件或分区匹配检查时被拒绝，不应通过修改检查逻辑绕过。
