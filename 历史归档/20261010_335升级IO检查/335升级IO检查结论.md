结论：当前程序不能作为“只允许通讯脚和明确允许的 IO 按配置输出”的通用客户模板。正常 Flash API 擦写调用没有发现随机写 GPIO 的执行路径，但 BOOT 存在演示引脚翻转、额外高电平输出、初始化切换顺序及 APP 交接状态的具体风险。

## 擦写正在执行与返回后的区别

[SCI_Boot.c:60](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/SCI_Boot.c:60) 的 program()以及79、82行擦除为同步调用，调用期间关闭普通中断。Flash API 占用 CPU 时，主循环 LED 任务不执行；回调 UpgradeWatchdog 只操作 WDKEY，不操作 GPIO。因此没有证据表明正常 Flash 忙期间会由这些任务不断翻转 GPIO。

但[Main.c:51](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/Main.c:51)使用 m_BaseTime -= C_TIME_05MS，而计时器继续运行。长擦除返回后主循环会补跑欠下的0.5ms任务，每4次又调用2ms任务。因此 LED 的多个翻转周期可能集中发生，不能继续把它解释为稳定的500ms闪灯。以LED计数从零开始、阻塞2秒为例，逻辑上约欠1000次2ms任务，可补跑4次翻转；具体脉冲间隔尚未实测。

写入失败、擦除失败或MD5失败路径返回协议错误，没有进入专门的安全 IO 状态。

## 初始化与直接跳转风险

现在先设DIR输出，再写SET高；如果数据锁存器是低/旧值，输出使能瞬间可能先驱动旧值，随后才变为高。应在允许的输出引脚上先预置需要的电平，再切换复用/方向；涉及已有外设输出时，还需控制原外设及交接顺序。

TI F2833x编程参考 [SPRUI07第119页GPADIR、第124页GPATOGGLE](https://www.ti.com/lit/ug/sprui07/sprui07.pdf#page=119) 明确区分输出锁存器与引脚驱动：输入态写TOGGLE不等于外脚翻转；DIR变输出后驱动当前锁存器值。本结论结合本工程进芯GPIO寄存器访问使用；实际脉冲仍需进芯板卡测量。

进芯 [AVP32F335数据手册V3.0](C:/Users/17879/Documents/ChatGPT/进芯替代TI%20C2000系列芯片信息/AVP32F335/01_数据手册/AVP32F335数据手册v3.0_202605.pdf) 正文13页（PDF23页）说明：GPIO有可配置内部上拉，GPIO0–11复位时不启用，GPIO12–87复位时启用。因此“配置输入”也不能等同于外部电路一定安全，尤其是高有效的使能信号；需结合外部上下拉和驱动使能条件。

[SCI_Boot.c:229](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/SCI_Boot.c:229) 的 jump只关闭中断、PIE、SCI和看门狗，没有复位GPIO/MUX/DIR。

30m当前示例APP已关闭SCI初始化及报文处理，使用上电/复位进入BOOT时，不应把26/27直接跳转继承风险当成该路径必然发生。33.3m APP仍支持0x72直接跳BOOT，APP已将26/27设为输出，这条路径能让BOOT的TOGGLE实际作用到引脚。BOOT关闭TBCLKSYNC和ePWM时钟，不等价于将客户功率输出强制到明确安全电平。

## Flash 执行位置与异常边界

- API库 .text/.econst 运行在RAML0，0x8000–0x8542；ramfuncs为0x8543–0x85ED；看门狗回调为0x85DF。两套现存MAP/OUT均已核查。
- Flash_Program/Verify及Flash_Erase调用以DINT/EINT保护；回调PUSH/POP ST1保留API状态。
- 实际API在脉冲执行阶段有DisableNMI及原值恢复，不能只凭DINT就断言此库缺少NMI防护。
- 未发现升级主流程调用Flash_ToggleTest；头文件有声明不代表实际执行。
- API初始化会关闭看门狗，这是进芯Flash应用报告明确描述的行为。现BOOT只在主循环开始前EnableDog，API返回后未重新使能；回调只喂狗，不能重新开启已关闭的看门狗。若API卡死，没有这里的看门狗复位兜底。
- 默认异常中断处理ESTOP/死循环，没有专门的功率输出关断。不能据此认定正常擦写会随机翻转，但也不能承诺任何异常下所有客户IO都安全。
- 有效APP标志先失效、完成MD5后才提交；一般擦写/校验失败不会正常请求启动无效APP。

共享UpgradeLayout.h当前选择0x308000。30m当前BOOT/APP OUT使用0x308000；33.3m现存BOOT/APP OUT仍使用0x300000，它们自身成对一致，但未按现共享配置重新生成。该差异已由UpgradeJumpApp立即地址及APP链接入口确认，不能只按共享头文件判断已烧板卡的地址配置。

IO翻转和初始化结论已分别通过两套OUT独立核实，不依赖上述地址差异。

## 建议处理范围

1. 从通用BOOT取消未明确允许的演示输出和翻转，GPIO26/27不应因一段LED代码被隐式操作。
2. 明确唯一通讯引脚与客户允许的输出清单；安全电平、上下拉、复用及异常处理按实际电路确定，不能默认所有引脚都拉低或拉高。
3. 对保留输出先预置电平，再启用输出；擦写前和失败后维持同一安全状态。
4. 处理APP直接跳BOOT的GPIO和外设遗留；停止PWM时使用明确输出关断，而不是仅停时钟。
5. 取消长擦写后补跑GPIO闪灯，或在升级期间冻结相应任务并重置时间基准。
6. 修改后需测量上电、进入BOOT、开始擦除、包间写入、擦写失败/断电、结束跳APP的关键波形。逻辑与编译/模型检查不能代替这项实板确认。

本轮仅形成检查结论，未擅自改变客户未知引脚电平，也未改动两边BOOT/APP。
