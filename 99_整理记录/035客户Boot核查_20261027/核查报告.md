# 客户 AVP32F035 Boot 静态核查（2026-10-27）

适用：AVP32F035，用户确认是 069 核的 80 pin 版本。现象：分别烧录 Boot、APP 后无法正常进入 APP，本次不是在线升级触发。核查两个客户压缩包、随包 MAP/OUT、用户补充的 APP CMD 截图和原厂迁移说明；未修改客户源码，未重编译、烧录或实板验证。

## 1. 首要问题：Boot 跳转地址未与 APP 入口同步

### 后续现场反馈：反复复位，新增确认 Timer0 配置遗漏

用户后续确认已将 Boot 跳转目标改为 APP 入口，但仍反复复位，EEPROM 请求数组读为 00 00。进一步比对发现浮点版替换 Timer 驱动时遗漏了原工程的定时中断配置：

- ADP `sys_source/DSP2803x_CpuTimers.c` 的 InitCpuTimers 中 Timer0 PRD=1499、TIE=1；注释为 60 MHz 下 25 us。
- AVP `sys_source/F2806x_CpuTimers.c` 的 InitCpuTimers 使用 TI 默认 PRD=0xFFFFFFFF，仅初始化/停止/重载计数器，没有设置 TIE=1。
- InitSysCtrl 只调用 InitCpuTimers；main 的 StartCpuTimer0 宏仅清 TSS，不设置周期或开启 TIE。可读源码未调用 ConfigCpuTimer；随包 OUT 中虽存在 ConfigCpuTimer 函数体，也未见调用该函数。随包 UserVariableInit 反汇编未见补配 Timer0。
- 在 120 MHz、TPR=0 下，0xFFFFFFFF 对应约 35.79 秒一周期，远非预期 25 us；而 TIE 没有开启，中断喂狗路径本身无法按设计运行。
- main:103 已调用 EnableDog，WDCR=0x00A8；正常循环通过 f_KickDogM/f_KickDogI 与 cpu_timer0_isr 联合喂狗。Timer0 ISR 不进，主循环仅交接标志，不能持续正常喂狗，符合看门狗复位、变量重初始化、等待计数无法到20的现象。是否为客户板当前复位根因仍需修改后全速运行验证。

最小修正建议：在实际使用的 `sys_source/DSP2803x_SysCtrl.c` 中紧接 `InitCpuTimers();` 后增加 `ConfigCpuTimer(&CpuTimer0, 120.0F, 25.0F);`，以实际 SYSCLK=120 MHz 为前提。现有 main 仍负责 StartCpuTimer0 和 PIE/CPU 中断使能。ConfigCpuTimer 会设置周期2999、TIE=1并重载。

注意 ISR 通过 looptimes 交替执行 case0/case1，timer_1s 仅在 case0 增长，所以硬件周期应为25 us，软件计数节拍才是50 us。直接改成50 us会令20秒等待变为约40秒。验收：启动后PRD=2999、TIE=1、TSS=0；Timer0 ISR能正常进入，主循环持续运行且不再反复复位，等待计数可到20并执行APP跳转。未改客户源码、未编译或实板验证。

客户 APP CMD 截图：

```c
FLASHD : origin = 0x3D8000, length = 0x013FFE
BEGIN  : origin = 0x3EBFFE, length = 0x000002
```

因此 APP 普通 Flash 区为 0x3D8000～0x3EBFFD，入口预留 0x3EBFFE～0x3EBFFF。客户浮点 Boot 的 `F28069.cmd:109` 从 0x3EC000 开始，两个普通 Flash 分区可以衔接，并非此前待排查的区间重叠问题。截图只展示 MEMORY，仍需核实 APP 的 SECTIONS 中 `codestart : > BEGIN`，或 MAP 中 codestart 的实际装载地址。

然而浮点 Boot `user_include/main.h:5` 仍保留旧定点工程地址：

```c
#define C28Update (void(*)(void))0x3F1FFE
```

随包 OUT 反汇编再次确认，`_Ckfa_Wait` 内 0x3EC976 执行 `MOVL XAR7, #0x3f1ffe`，随后 `LCR *XAR7`。所以不是仅有未使用宏写错：随包机器码也确实调用旧地址。

**最小修正建议（未在本次执行）：**确认 APP codestart 链接在 BEGIN 后，将上述宏改为 `0x3EBFFE`，重新完整编译并重烧 Boot。保留 Boot 自己的 `BEGIN=0x3F7FF6`，不要将 Boot 的上电入口改成 APP 入口。核对最终 Boot OUT/反汇编，不能只修改头文件后仍烧旧 OUT。

另需检查 APP 是否输出 `csmpasswds`、`csm_rsvd`：截图中也定义了这些区域，实际是否写入须看完整 SECTIONS/MAP；这不等于普通代码区重叠。

## 2. 升级与跳转分别写什么

浮点工程相对目录：`Boot_AVP035/AEP-XKS48P1-II-DSPAVP035-Boot-Unlock_CKFA`。

| 存放位置 | 内容/作用 | 依据 |
|---|---|---|
| 外部 EEPROM 十进制 5001～5002，即 0x1389～0x138A | `01 02` 表示远程升级请求；上电据此决定停留 Boot | `user_include/eeprom_save_read.h:16`、`user_source/main.c:69` |
| 外部 EEPROM 十进制 5003～5004，即 0x138B～0x138C | `01 02` 表示升级已开始/进行中 | 同头文件:17、`main.c:78`、`scil_frame_deal.c:146` |
| RAM 0xBFFA～0xBFFF（六个 16 位 word） | 跳 APP 前 Boot_encryption 写四个随机数和两个变换结果，应与 APP 的握手校验匹配 | `Boot_ file_ encryption.c:16`、:23、:54；`F28069.cmd:133`、:149 |
| RAM 0xBFF9 | Boot 版本变量，源码初始化为 102 | `Boot_ file_ encryption.c:18`、`F28069.cmd:134`、:150 |
| 通信帧/当前 Flash 写入块 | HEX 行累加和、Flash_Verify 和逐 word 回读比较 | `scil_frame_deal.c:143`、`crc_sum_check.c:125`、`Example_Flash2806x_API.c:235` |

**结论：升级流程写 EEPROM 状态标志；真正调用 APP 前还会写 RAM 握手校验数据。没有发现把整包 APP CRC 写到 Flash、上电再验证整包有效性之后才跳转的逻辑。RAM 握手也不是 APP 镜像完整性校验。**APP 是否正确接收并保留 RAM 握手，需要 APP 源码进一步确认。

## 3. 直接烧录时，EEPROM 同样影响是否到达跳转指令

`main.c:69`：5001～5002 为 `01 02` 时 `CKFA_Wait_flg=0`，不会走正常等待后跳转；否则置 1。`main.c:255` 的 Ckfa_Wait 累计到 20 次后依次执行 Boot_encryption、StopInterrupt、C28Update。只有定时周期正确时，20 次才相当于约 20 秒。

因此先观察 `Ckfa_state_28034[0..1]`、`CKFA_Wait_flg`、`CKFA_Wait_cnt` 和实际 PC。分别烧录 Flash 不代表外部 EEPROM 被清空；残留 `01 02` 可使 Boot 正常循环而不进入跳转。不要未备份就整片清空 EEPROM，其中还包含 ADC 校准参数。

若 PC 已执行调用 APP：检查目标是否为 0x3EBFFE，并读取该地址两个 word；单步应进入 APP 的启动分支，依次跟踪 APP `_c_int00` 和 `main`。若仍进入 APP 后异常，再核对 APP RAM 握手初始化、启动代码、Flash/RAM 段复制。

在线升级的退出流程是另一条路径：最后一包成功仅清 RAM `f_start_update`（`main.c:202`），并不直接跳 APP；必须处理退出帧 `00 00 00 33 01 00 34`（`scil_frame_deal.c:105`），将 5001～5004 写为 `0F`，读回后置 `f_ckfa_stop`，由看门狗复位，再走上电等待跳转。这个流程不应套作本次直接烧录故障的既成原因。

## 4. 另外两项确定的在线升级移植缺陷

这两项需要处理，但不能据此认定它们造成了本次直接烧录后的跳转失败。

1. **仍链接 TI 原版 Flash API。**客户 `lib/Flash2806x_API_V100.lib` 与本机 TI controlSUITE 原库 SHA256 相同：`8CE2163DB73517A5D47186B3249F3E4B8E97E9EDA837B6503022DD673D68039A`。不同于本机进芯适配库 `Flash2806x_API_V100_FLASH.lib`。原厂迁移说明的“软件差异②③”明确要求 Flash 操作更换进芯 AVP069 库；库身份核对路径及哈希见 CSV。当前库可能还有版本要求，更换时应使用目标芯片适配版本。
2. **API 本体未搬 RAM。**随包浮点 MAP:104、:105、:117 显示 Program=0x3ECBC3、Erase=0x3ECCA4、Verify=0x3ED22E，均在 Flash 的 `.text`。MAP:146 起仅包装器等位于 ramfuncs，运行地址 0x8000；CMD:156 及 `DSP2803x_SysCtrl.c:57` 只复制 ramfuncs。必须将实际使用的 API 代码及需要的数据整体安排到安全 RAM，并在调用前复制，不能只给包装器加 CODE_SECTION。原 ADP 工程调用的是 ROM API，移植成外部 API 函数体后不能沿用原搬运范围。

实际 Debug 排除了 `user_source/Flash2803x_API.c` 和 `sys_source/F2806x_SysCtrl.c`（`.cproject:80`），在用的是 `Example_Flash2806x_API.c` 和已换 F2806x 头的 `DSP2803x_SysCtrl.c`；不能因为目录里还留旧文件名就判断运行的是旧 API 包装实现。

## 5. 其他核对结果与遗留风险

- 外部晶振路径、PLL=12、DIVSEL=3、延时与 API 的 CPU_RATE=8.333 ns；若实际晶振为 10 MHz，则 120 MHz 自洽。实际晶振尚未提供。
- 实际 Flash 等待为 4/4/7，比知识库当前量产口径 3/3/5 更保守，不能直接定为跳转根因。ADC CLKDIV2EN=1。
- 没启用 FPU32 本身不代表整数 Boot 无法在浮点核执行；工程元数据残留 F28034 也不能独立证明本次故障。
- IQ 表地址仍沿用 TI 方案，当前 MAP 未见使用相应表，不作为本次已证实原因。
- 原 ADP 与移植版共享的旧风险：跳转未联锁升级进行中标志及 APP 完整性；EEPROM PageWrite 忽略 ACK；退出读回不要求四字节均为 0F；FlashProgramApi 将连续六个合法 0xFFFF 也判作 PROGRAM_FAIL2；HEX 写入目标缺少 APP 上下界保护。这些应另行收敛处理，不在本次审查中扩大修改。
