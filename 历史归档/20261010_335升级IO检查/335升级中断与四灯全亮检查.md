用户补充的现场事实：升级烧录时曾断电；重新上电后四灯一直全亮，但可以直接开始升级；另一次第一个灯与其余三个灯交替闪，也可以继续升级。串口一直连接，JTAG 已拔。尚不明确串口是 TTL 直连还是经 RS232 收发器、是否接了 VCC，以及实际烧入哪一对 BOOT/APP。

结论：现有升级流程具有“未完成不提交有效标志”的逻辑保护，正常断通讯通常可以重新全量升级。但不能据此保证任意擦写断电后 APP 和 IO 都安全；灯状态有软件解释线索，未查明现场根因。能继续升级说明恢复入口仍可用，不证明所有 GPIO 安全或断电复位完整。

## 断通讯与断电后的升级状态

两种晶振工程的 SCI_Boot.c 当前内容一致。

- [SCI_Boot.c:69](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/SCI_Boot.c:69)：开始升级先将原有效标志 0xAA 编为 0 并验证，再擦 B 扇区，随后擦 APP 配置范围。
- [SCI_Boot.c:104](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/SCI_Boot.c:104)：收齐固件、从 Flash 计算全量 MD5 与上位机提供的值相同后，才写入并验证 0xAA。
- [SCI_Boot.c:139](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/SCI_Boot.c:139)：完整有效请求会清除自动跳 APP 标志。没有升级会话超时后自动恢复 APP 的逻辑；接收半帧超时仅清报文缓存。
- [FunctionMain.c:80](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/FunctionMain.c:80)：重新上电自动跳 APP 只判断单字标志是否等于 0xAA，没有重新校验 APP 的长度、CRC 或 MD5。

| 中断阶段 | 源码层面可判断的行为 |
|---|---|
| 仅握手，尚未发开始擦除命令 | 旧 APP 未改；断通讯不复位会留 BOOT；复电后有效标志仍为 AA 时可启动旧 APP |
| 原有效标志已经成功编 0，但 B 尚未擦除 | 旧 APP 尚未擦写，但标志无效，复电留 BOOT |
| B 已成功擦除，后续 APP 擦写/传包未完成 | 标志为擦除值 FFFF；断通讯不会提交 AA，留 BOOT，重新全量升级 |
| 新 APP MD5 已通过且 AA 已成功落地 | 软件流程认为新 APP 已完整，复电可启动 |
| **B 扇区正处于物理擦除时突然断电** | **标志与该扇区内容不能由 C 源码限定；不能承诺标志必定不等于 AA** |

关键缺口：有效标志 0x337FFE 就在 B 扇区，B 也属于 APP 尾部范围。先把标志编 0，并不能证明随后的物理擦 B 中断后必定保持无效。启动只比较一个字，因此缺少对误判有效标志的进一步防线。这里是保护能力的边界，不是已经证实现场读出了 AA。

正常升级掩码排除存放 BOOT 的 A 扇区。恢复方式是重新开始一轮升级，从包 0 全量擦写并校验，不支持断点续传。恢复成功仍取决于供电稳定、BOOT/Flash 正常；“正常操作不擦 BOOT”不能扩展成异常电压下 BOOT 永远不受影响。

## 两种灯现象能解释到什么程度

[BOOT FunctionMain.c:29](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/FunctionMain.c:29) 在同一次任务调用中连续翻转 GPIO24、25、27、26，正常空闲计时下约每 500ms 翻转一次。[APP FunctionMain.c:29](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/app/Main/FunctionMain.c:29) 只翻转 GPIO27。

如果四灯确实接这四脚、四脚均为输出，并且进入 BOOT 时一灯的初始状态与其余三灯相反，那么一起翻转后就会出现“一灯亮/三灯灭”与“一灯灭/三灯亮”交替。这与用户第二种观察相容，但不证明状态差异一定来自 APP 或串口残余供电。

[BOOT HardwareSetup.c:500](C:/Users/17879/Desktop/CHIP/BOOTLOADER/335_BOOT_APP/335_BOOT_APP/30m/boot/Main/HardwareSetup.c:500) 仅明确初始化灯相关 GPIO24、25，未完整初始化 GPIO26、27。真正硬复位后，26、27 为输入时，TOGGLE 只改变输出锁存器；APP 直接进入 BOOT 时，则可能继承输出方向。不能把四灯翻转当作每一种冷上电路径必然发生的行为。

“一直全亮”尚不能由正常空闲的周期翻转充分解释。同步 Flash 调用会暂时阻塞主循环、暂停闪灯，长擦除返回后还会补跑任务；但这不足以解释空闲时持续全亮。需要核对实际灯接线、烧入的 OUT、GPIO MUX/DIR/锁存状态和复位波形，不能仅凭灯亮判定 CPU 跑飞、Flash API 随机改 GPIO，或 APP 已损坏。

参考板 AVP32F335_EVM Rev2.0 用户手册 PDF 第 16 页、正文第 13 页表 3-1 将 DS3/DS4/DS5/DS6 映射到 GPIO27/26/25/24，均低有效。用户板型号和接法未确认，该接法只能作为对照。

## 串口未拔与电源复位约束

[AVP32F335 V3.0 数据手册](<C:/Users/17879/Documents/ChatGPT/进芯替代TI C2000系列芯片信息/AVP32F335/01_数据手册/AVP32F335数据手册v3.0_202605.pdf>) 的明确要求：

- PDF 第 120 页、正文第 110 页 6.8：断电时，XRS 必须在 VDD 降至 1.5V 之前至少 8μs 拉低。
- 同页：未供电时，数字脚电压不能超过 VDDIO+0.7V；未供电引脚被施加电压可能产生不可预料结果。VDDIO 与 VDDA 压差须在 0.3V 内。
- PDF 第 122 页、正文第 112 页表 6-9：上电还需满足 XRS 保持时间与稳定时钟条件。
- PDF 第 43 页、正文第 33 页 3.3.18：复位时 GPIO 为输入；PDF 第 23 页说明不同 GPIO 的复位上拉状态。输入/高阻不等于外部负载一定关闭。

串口仍连接使“板子已经彻底断电”不能仅凭拔主电源确定。如果存在串口 VCC 连接，或 TX/RX 经板上保护/收发器路径供电，可能影响掉电及复位；目前没有电路或电压证据证明已经发生。JTAG 已拔可排除这一现场的 JTAG 连接，但不能排除串口或其他接口。

B0 电源排序说明包含欠压时 GPIO 输出缓冲器关闭、高阻的描述；适用型号和具体 BIN0/BIN1 供电排序仍应按出货料号核对，不直接套用为所有 335 的无条件保证。当前没有把旧 XINTF/WDFLAG 案例作为此故障根因。

## 建议的核对与处理

1. 先保留当前异常状态、烧入文件和上位机日志。能读出时记录有效标志、PC、灯 GPIO 的 MUX/DIR/DAT；避免先全擦把现场覆盖。
2. 拔掉串口及其他可能供电的接口，确认 3.3V/1.8V 确实降至接近 0 后再独立上电，对比灯状态。若再次异常，抓取两路电源与 XRS 的断电、再上电波形；不要把一次现象消失当作根因证明。
3. BOOT 应只操作明确允许的引脚；删除或隔离演示闪灯、建立上电/升级/失败时一致的 IO 状态，并处理 APP 交接。安全电平须由实际负载确定，不能统一全部拉低或拉高。
4. 若要求抵御任意升级断电，应补充上电 APP 完整性校验和可靠提交机制；这会涉及 BOOT/固件布局，需要单独实施和验证，当前没有修改。
5. 软件不能替代板级欠压复位、接口供电隔离和负载默认关断条件。客户要求的“其他 IO 始终安全”需要硬件条件和实测一起确认。
