1.用 法 PIE：写入 PIEACK 和手动清除 CPU 中断掩码连续操作会引起虚假的中断嵌套。
影响范围 所有版本
详 述 用于中断嵌套的某些代码顺序会让 CPU 和 PIE 进入不一致的状态，从而触发不需要的中断。进入此状态所需的条件是：
1. PIEACK 清除后立即显示启用全局中断（EINT 或 asm（“ CLRC INTM”））。
2. 嵌套中断为其组清除一个或多个 PIEIER 位。
是否触发不需要的中断取决于系统中其他中断的配置和时序。在大多数应用程序中，这应该是一个罕见或不存在的事
件。如果发生这种情况，不需要的中断将是嵌套中断的 PIE 组中的第一个中断，并将在嵌套中断重新启用 CPU 中断（EINT
或 asm（“ CLRC INTM”））后被触发。
解决方案 在 PIEACK 写入和 CPU 中断启用之间添加 NOP。示例代码如下所示。
//Bad interrupt nesting code
PieCtrlRegs.PIEACK.all = 0xFFFF; //Enable nesting in the PIE
EINT; //Enable nesting in the CPU
//Good interrupt nesting code
PieCtrlRegs.PIEACK.all = 0xFFFF; //Enable nesting in the PIE
asm(" NOP"); //Wait for PIEACK to exit the pipeline
EINT; //Enable nesting in the CPU
2.用 法 CAN 引导加载程序：内部振荡器容差不足以支撑高温下 CAN 的正常运行。
影响范围 所有版本
详 述 设备 Boot-ROM 中的 CAN 引导加载程序使用内部振荡器作为 CAN 时钟源。在高温下，内部振荡器的频率可能会偏离
较大，从而影响 CAN 消息的接收，导致通讯异常。
解决方案 在调用 CAN 引导加载程序之前重新校准内部振荡器。这可以在应用程序代码中完成。为了获得更大的灵活性，可以将
包装器功能编程到器件的 OTP 存储器中。
3.用 法 FPU32 和 VCU 先后对内存访问。
影响范围 所有版本
详 述 当 VCU 内存访问和 FPU 内存访问先后发生时，此用法说明适用。有三种情况：
情况 1：
连续内存读取：先由 VCU 指令（VMOV32）执行一次读取，随后 FPU32 指令（MOV32）执行一次读取。如果在第一次
读取期间流水线 R1 阶段发生停顿，则第二次读取将锁定错误的数据。如果第一条指令在 R1 阶段未停止，则第二次读
取将正确进行。
指令的顺序（FPU 后跟 VCU 或 VCU 后跟 FPU）无关紧要。任何一次读取访问的内存地址也无关紧要。
情况 1 解决方法：在两个连续的读取指令之间插入一条指令。可以使用除 VCU 或 FPU 内存读取以外的任何指令。
情况 1，示例 1：
VMOV32 VR1,mem32 ; VCU memory read
NOP ; Not a FPU/VCU memory read
MOV32 ROH,mem32 ; FPU memory read
情况 1，示例 2：
VMOV32 VR1,mem32 ; VCU memory read
VMOV32 mem32, VR2 ; VCU memory write
MOV32 ROH,mem32 ; FPU memory read
情况 2：
连续内存写入：先由 VCU 指令（VMOV32）执行一次写入，随后 FPU32 指令（MOV32）执行一次写入。如果在第一次
写入期间流水线停止，则第二次写入可能会损坏数据。如果第一条指令在写入阶段没有停止，则不会发生损坏。

2.通 告 FPU：FPU 到 CPU 寄存器移动操作之前的任何 FPU 2p 操作
影响范围
描 述 当多周期（2p）FPU 指令后跟 FPU 到 CPU 寄存器传输时，此通报适用。如果 FPU 到 CPU 读取指令源寄存器与 2p 指令
目标相同，则在 2p 指令完成之前，读取的值可能是 FPU 寄存器的值。发生这种情况是因为 2p 指令依赖于在管道的 E3

3.通 告 FPU：LUF、LVF 标志对于 EINVF32 和 EISQRTF32 指令无效。
影响范围
描 述 此通报适用于 EINVF32 和 EISQRTF32 指令。这些说明的预期结果是正确的;但是，下溢 （LUF） 和溢出 （LVF） 标
志不是。这些标志无效，不应使用。
LUF 和 LVF 标志无法使用 C 代码访问，因此此通报的总体影响预计很小。如果用户选择在程序集中将这些标志（例
如，在对时间关键型算法进行编码时）作为混合 C/ASM 项目的一部分，则用户将需要使用这些标志禁用围绕程序集
代码的中断，并且还需要通过使用 EINVF32 或 EISQRTF32 指令来保留这些标志。
解决方案 在 C 代码中使用这些标志没有解决方法，并且由于编译器和工具用法说明中提出的原因，应将其视为无效。
此处显示的解决方法提供了一种在仅程序集代码中使用 EISQRTF32 和 EINVF32 时保留 LVF、LUF 标志的方法。
不要依赖 LUF 和 LVF 标志来捕获由 EINVF32 和 EISQRTF32 指令引起的下溢/溢出情况。相反，在使用每条指令之前，
请检查操作数的以下条件（在代码中）: EINVF32 Divide by 0
EISQRTF32 Divide by 0, Divide by a negative input
通过在调用指令之前将标志保存到堆栈中，然后一旦指令完成，然后恢复标志的值，忽略 LUF 和 LVF 标志的内容。
如果 PIE 中断绑定到 LUF 和 LVF 标志，请在使用 EINVF32 或 EISQRTF32 指令之前禁用中断（在 PIE 上）。检查是
否设置了 LUF 和 LVF 标志;如果是，则可以设置一个变量来指示检测到错误的 LUF/LVF 条件。在重新启用中断之前，请
清除 STF（FPU 状态标志）中的标志。
一旦在 PIE 上重新启用中断，就可能发生中断（如果两条指令中的任何一条断言了 LUF/LVF 中断线路），并执行分支
到中断服务例程 （ISR）。检查标志以确定是否发生了错误情况;如果有，请忽略中断。
不要直接清除 PIE IFR 位（锁定 LUF 和 LVF 标志），因为同一 PIE 组（PIE 组 12）上的中断事件可能会无意中丢失。

有关编译器和工具用法的说明
编译器不使用 LVF/LUF 作为条件指令的条件代码，运行时支持（RTS）库也不以任何方式测试 LVF/LUF。
编译器可能会生成修改 LVF/LUF 的代码，这意味着 STF 寄存器（包含这些标志）的值在函数边界处未定义。因此，尽
管库中的 sqrt 例程可能会导致设置 LVF/LUF，但在 CGT 中不能保证用户可以在 sqrt 返回后读取这些位。
尽管编译器确实提供了__eisqrtf 和__einvf32 内部函数，但它不提供读取 LVF/LUF 位或 STF 寄存器的内联函数。因此，
用户无法从 C 代码访问这些位。

外设假定在模块输入上存在与 SYSCLKOUT 的外部同步。例如，QPOSCNT 可能无法正确复位或锁存，并且输入引脚上
的脉冲可能会丢失。
为了 eQEP 模块的正常工作，输入 GPIO 引脚应通过 GPxQSELn 寄存器配置为同步输入模式（带或不带限定），这是
GPxQSEL 寄存器在复位时的默认状态。TI 提供的所有现有 eQEP 外设示例还将 GPIO 输入配置为同步输入模式。
异步模式不应用于 eQEP 模块输入引脚。
解决方案 配置配置为非异步模式的 eQEP 引脚的 GPIO 输入（除“11b = 异步”之外的任何 GPxQSELn 寄存器选项）。
23.通 告 eQEP：GPIO25 引脚上的 EQEP2B 功能操作不正确（此通报仅适用于 100 引脚封装。
影响范围
描 述 当 GPIO25 引脚配置为 EQEP2B 功能时，无论为 MFSXA 操作配置了哪个 GPIO 引脚，MFSXA 引脚上的活动都将反
映在此引脚上。仅当 GPIO25 引脚配置为 EQEP2B 操作时，才会出现此问题。当 GPIO25 引脚配置为 GPIO、ECAP2

24.通 告 eQEP：在指数期间方向变化时，位置计数器错误地复位
影响范围
描 述 使用 PCRM = 0 配置时，如果在索引输入处于活动状态时发生方向更改，则位置计数器 （QPOSCNT） 可能会被错误
地重置，从而导致计数器值发生意外变化。这可能导致从持仓计数器的预期值更改多达 ±4 个计数，并导致错误标志
的意外后续设置。
使用 PCRM = 0 配置 [即，索引事件时的位置计数器复位 （QEPCTL[PCRM] = 00）]时，如果在向前移动期间发生索引
事件，则在下一个 eQEP 时钟上将位置计数器重置为 0。如果索引事件发生在反向移动期间，则位置计数器将在下一
个 eQEP 时钟上重置为 QPOSMAX 寄存器中的值。eQEP 外设记录 QEPSTS 寄存器中第一索引事件标记（QEPSTS[FIDF]）
上第一索引标记（QEPSTS[FIDF]）的出现和方向。它还会记住第一个索引标记上的正交边沿，以便将相同的相对正交转
换用于索引事件重置操作。
如果在索引脉冲处于活动状态时发生方向变化，模块仍将继续寻找相对正交转换以执行位置计数器复位。这会导致仓
位计数器值发生意外变化。
解决方案 如果在索引处于活动状态时可能发生方向更改，并且位置计数器值的由此变化可能会影响应用程序，则不要使用 PCRM
= 0 配置。
用于执行位置计数器重置的其他选项（如果适用于应用程序）[如索引事件初始化 （IEI）]）没有此问题。

25.通 告 eCAN：中止未设置确认位
影响范围
描 述 将传输请求重置（TRR）寄存器位设置为中止消息后，在极少数情况下，TRRn 和 TRSn 位将在不设置中止确认（AAn）
位的情况下清除。传输本身已正确中止，但不会断言中断，也不会指示挂起的操作。
为了发生这种罕见的情况，必须发生以下所有情况：
 上一条消息未成功，原因可能是仲裁丢失，要么是总线上没有节点能够确认它，要么是传输导致错误帧。
上一封邮件不必来自当前尝试传输中止的同一邮箱。
 邮箱的 TRRn 位应设置在紧随设置 TRSn 位的周期之后的 CPU 周期中。由于传输不完整而设置的 TRSn 位也满足此条件;也就是说，TRSn 位可以在过去设置，但传输仍然不完整。
 TRRn 位必须设置在精确的 SYSCLKOUT 周期中，其中 CAN 模块处于空闲状态一个周期。CAN 模块在不接
收或传输数据的过程中，称为空闲状态。
如果发生这种情况，则在设置 TRR 位后，邮箱的 TRRn 和 TRSn 位将清除 tclr SYSCLKOUT 周期，其中：
tclr = [(mailbox_number) * 2] + 3 SYSCLKOUT cycles 如果发生这种情况，则不会设置 TAn 和 AAn 位。通常，TA 或 AA 位在 TRR 位变为零之后设置。
解决方案 发生此问题时，TRRn 和 TRSn 位将在 tclr SYSCLKOUT 中清除
周期。要检查此情况，请首先禁用中断。在设置 TRRn 位后，检查 TRRn 位 tclr SYSCLKOUT 周期，以确保它仍然设
置。设置 TRRn 位表示问题未发生。
如果 TRRn 位被清除，则可能是因为消息的正常端，并且设置了相应的 TAn 或 AAn 位。检查 TAn 和 AAn 位。如果设置
了其中任何一个位，则问题未发生。如果它们都为零，则问题确实发生了。像中断服务例程一样处理这种情况，只是
AAn 位现在不需要清除。
如果设置了 TAn 或 AAn 位，则在重新启用中断时将发生正常的中断例程。
