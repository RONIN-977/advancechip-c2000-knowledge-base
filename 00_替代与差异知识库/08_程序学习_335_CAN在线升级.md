# AVP32F335：CAN 在线升级程序学习

更新时间：2026-09-23。范围只包括库内 `335boot_app_1vsduo` 的 BOOT、APP、上位机协议表及一对多说明；以下为源码静态分析，尚未在芯片和 CAN 总线上验证。此工程是升级实现参考，不等同于经过确认的量产固件。335 当前出货 B 版及其他硬件规则仍以 [差异学习笔记](<02_差异学习笔记.md>) 和最新版手册为准。

## 工程入口和存储分区

- [BOOT 主循环](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/App/Src/main.c>)：初始化时钟后先 `Jump_Check()`；无有效 APP 或收到返回 BOOT 的 RAM 标志才留在 BOOT。留在 BOOT 后初始化定时器、CAN、Flash API，主循环轮询 CAN 邮箱并处理协议，10 ms 任务处理延时跳转及 Bus-off 恢复。
- [APP 主循环](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_APP_CAN/UserCode/App/Src/main.c>)：CAN 接收由中断入队，1 ms 任务处理协议，10 ms 任务处理 APP→BOOT 延时跳转。主文件里的 `test_const_data[0x28000]` 用于增大测试程序体积，不是升级必需逻辑。
- [BOOT CMD](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/Library/CMD/AVP32F335_FLASH.cmd>) 与 [APP CMD](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_APP_CAN/Library/CMD/AVP32F335_FLASH.cmd>)：BOOT 在 `0x338000` 起，启动入口 `0x33FFF6`；APP 入口 `0x300000`，APP 正文从 `0x300002` 起；`0x330000–0x330002` 保存 APP 长度（2 word）和 CRC（1 word）。`0x00FFFE` 的 RAM 字用于 APP/BOOT 跳转请求。地址均为 C28x 字地址。
- `APP_FLASH_LENGHT=0x02FFFE`，约 196606 word；[头文件](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/Com/Inc/dsp_program.h>) 旁注的“160k word、320KB”与宏值不符，核对容量应以 CMD/手册为准。

## 随工程提供的基础例程

本节只说明 CAN BOOT/APP 工程附带的基础示例。用户随后补入独立的 [Rev2.0 开发板例程](<09_程序学习_335_Rev2.0例程.md>)，其中包括 ADC、PWM、CAN、SCI 等 13 个工程；不能再把本 BOOT/APP 包当作 335 唯一例程。后续遇到具体外设应用时仍需结合目标板和最新版手册核对。

- [时钟与 Flash 初始化](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/App/Src/dsp_base.c>)：入口先拷贝 `ramfuncs` 到 RAM，再配置 PLL、外设时钟、Flash 等待值及 PIE。`CPU_RATE`、PLL、等待值和实际晶振必须成套修改；不能直接照搬文件中的 150 MHz 注释。
- [GPIO/LED](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/HardWare/Src/gpio_config.c>)：GPIO27 配成普通输出，10 ms 任务驱动状态灯；这是升级板的状态指示例程，不代表所有 335 板卡的 LED 都接 GPIO27。
- [定时器与中断](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/HardWare/Src/timer_config.c>)：CPU Timer0 配置为标称 1 ms 心跳，ISR 设置任务标志和系统 tick。该工程的 `TIMER0_CLOCK=60`，移植到其他主频时要同步修改。
- [eCAN 配置](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/HardWare/Src/can_config.c>)：选用 eCAN-A，标准帧，MBOX0 发、MBOX16 收；底层引脚复用在 `AVP33x_ECan.c` 中配置为 GPIO18/CANRXA、GPIO19/CANTXA。BOOT 轮询接收，APP 用中断接收；两边的收帧机制不同，复制代码时不能漏掉对应的 PIE/邮箱设置。
- [Flash API 调用](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/Com/Src/dsp_program.c>)：展示 CSM 解锁、API 从 Flash 搬到 RAM、擦写后逐段 `Flash_Verify` 的结构。这是 APP 区升级例程，不是任意 Flash 扇区写入模板；使用 335B 时需核对对应 API 库及工程配置。

## 一次升级的实际路径

1. 根据 [协议表](<../AVP32F335/335boot_app_1vsduo/335boot_app/上位机/CAN帧协议_特供.xlsx>)，CAN 使用标准帧：主机请求 `0x7A0`，设备响应 `0x7B0`；BOOT 用 MBOX16 轮询接收、MBOX0 发送，APP 用接收中断。工程注释指定 500 kbit/s；实际波特率要连同外部晶振、PLL 和 CAN 位时序复核。
2. `0x10/0x04` 搜索设备，`0x10/0x05` 按 16 位设备 ID 选择节点；`0x10/0x03` 进入扩展会话，`0x27/0x01–02` 进行种子/密钥交互。若从 APP 启动，`0x10/0x02` 使匹配本机 ID 的 APP 延时跳至 BOOT，然后重新建立会话及解锁。密钥由工程内固定常量与种子异或生成，只是这份工程的协议实现。
3. BOOT 的 `0x34` 从请求读取固件字节长度、除以 2 转成 word，与 APP 上限比较，再调用 Flash API 擦除 H 至 B 扇区。`0x36` 将收到的字节按低字节在前组成 16 位 word，逐块 `Flash_Program` 并 `Flash_Verify`，成功才推进写地址。[协议实现](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/Com/Src/CAN_upgrade_protocol.c>)、[Flash 操作](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/Com/Src/dsp_program.c>)。
4. `0x37` 比较主机 CRC 与 Flash 内容计算结果，成功才把长度和 CRC 写入 `0x330000–0x330002`。`0x11` 延时约 50 ms 跳至 APP。以后 BOOT 上电先据长度和 CRC 校验 APP；APP 请求回 BOOT 时写 `0xAA02` 到 RAM 标志并跳到 `0x33FFF6`。CRC 计算实现每个 16 位 word 只取**低 8 位**参与查表；不能直接假设通用的“所有 BIN 字节 CRC16”与之兼容，主机算法必须逐项对照。[CRC 实现](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/Com/Src/crc_verify.c>)。
5. [一对多说明](<../AVP32F335/335boot_app_1vsduo/335一对多升级说明.docx>)要求各板分别设置唯一 `proto_data.local_id` 并预烧 BOOT；文中示例两块板、分别用 ID1/ID2。源码当前把 `local_id` 固定为 `4`，还留有“获取设备 ID”的 TODO，量产必须接入稳定唯一的设备标识。说明中“节点升级”经过演示，“一键升级”因缺客户外部 ID 条件未测试；并要求擦除超时预留 12 秒，1.07a 为一对多 CAN 特供版本。

## 使用前必须核查的代码问题

| 问题 | 源码证据及影响 |
|---|---|
| 选中节点只限制回复，不限制执行 | `0x10/0x05` 只设置 `Index`，而 `0x34/0x36/0x37` 的擦、写、校验条件只有扩展会话与解锁，`Index` 只包围响应发送。多节点共享 `0x7A0` 时，未选节点仍可能执行升级命令。APP 中也保留擦写服务；上位机“选择节点”不能单独作为隔离保证。上线一对多前必须在收帧/服务执行路径验证并修正节点隔离。 |
| 进入编程会话依赖先前数据 | 协议表把 `0x10/0x02` 请求写成 `02 10 02 ...`，但 APP 源码立即读取 `RxDataBuf[0:1]` 作为目标设备 ID；此短帧没有这两个数据字节。若此前发送过 `0x10/0x05`，缓冲区可能保留上次的选中 ID，工程可能正是依赖这一点。需要核对实际特供上位机帧序列，不能把此短帧当成可独立执行的命令。 |
| 时钟配置注释与实际值冲突 | 工程假设外部 `30 MHz`，`DSP28_PLLCR=4`、`DIVSEL=2`，计算为 `60 MHz`；`TIMER0_CLOCK=60`、`CPU_RATE=16.667 ns` 也指向 60 MHz，但 `SYSCLKOUT_MHZ=150`、`CPU_FRQ_150MHZ=1` 和多处注释标称 150 MHz。不能仅看宏名更改 PLL；Flash 等待、API scale、定时器、CAN 波特率必须按实测时钟联动核对。[时钟宏](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/Library/Per_Inc/AVP33x_Examples.h>)、[定时器](<../AVP32F335/335boot_app_1vsduo/335boot_app/demo/AVP32F335_BOOT_CAN/UserCode/HardWare/Src/timer_config.c>)。 |
| 传输边界和序号未验证 | `RxDataBuf[256]` 对首帧声明的长度没有上限检查，续帧 `SN` 只读取不比较；协议表写了“序列号错误”负响应，但源码未实现。`0x36` 也没检查累计写入长度是否等于 `0x34` 声明值；`0x34` 对奇数字节长度直接向下取整。坏帧、重放或主机异常时，需验证不会越界或越区写。 |
| 文档和源码时序不一致 | APP 有空闲累计的会话超时逻辑，BOOT 相关逻辑被注释；协议表的“5 s 自动返回默认会话”不能直接视为 BOOT 实际行为。BOOT 发送前调用的 `CAN_Check_Txbuf_Empty()` 检查 TRS16，而实际发送邮箱为 0；应检查响应发送期间是否可能覆盖未完成的邮箱 0。 |
| Flash 库和运行位置 | 两工程链接名为 `Flash28335_API_V210.lib` 的库，`Flash28_API` 段从 Flash 复制到 RAM 后运行。此文件名不能证明该库已适配当前出货 335B；使用前应对照 335B 最新 Flash 指南与工程构建配置，确认库版本、时钟比例和 RAM 段。 |

本笔记不修改原始工程、上位机或 BIN。当前没有 CCS 编译、板级升级、断电恢复或双节点隔离测试结果；上述“可能”类影响是基于静态控制流判断。

## 2026-10-26 客户Flash镜像异常分析（独立项目）

见[369.out与四份DAT对照](../99_整理记录/335_Flash比对_20261026/OUT对照与原因分析.md)。该客户项目不据此认定使用上文BOOT/升级协议。导出0x300000–0x337FFF中，好件ram1/ram3与369.out已装载段一致；ram的45字差异全在.cinit，ram2的451字差异含315字.text和136字.cinit。启动反汇编及初始化记录解码表明两段.cinit异常位于_ApplicationObjDic（目标RAM0xD700）初始化数据，分别映射至RAM0xE519–0xE56E和0xE861–0xE974；可形成对象字典访问异常的静态机制。三个局部区呈向后错位两个16位字；差异发生阶段、读取链路及物理Flash状态仍需实板复核。用户确认XINTF勘误已排除，断电不恢复、重烧恢复；不将旧勘误作为当前故障解释。DAT未覆盖0x338000以上.econst/.switch/codestart，不声称整片Flash已核对。
