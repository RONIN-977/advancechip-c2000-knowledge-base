# 335：369.out 对照与现场故障分析

日期：2026-10-26。范围：用户提交的369.out、四份DAT、客户排查长截图，以及用户补充的现场事实。使用进芯知识库技能与TI C2000工具作文件分析；未连接本次客户板卡，未进行实板复读、烧录或运行验证。

## 当前结论

1. **在DAT覆盖的Flash装载区，ram1、ram3均与369.out完全一致。ram、ram2与该OUT存在确定差异。** 因此好坏件比较现在有了独立的OUT基准，不只是两个样品相互比较。
2. **ram坏件的差异全部属于.cinit中EtherCAT应用对象字典的初始化数据。ram2同时存在程序指令与对象字典初始化数据差异。** 这一点能从软件机制上解释部分通信数据访问异常，不能直接宣布已复现现场故障根因。
3. 三个局部区域均呈连续向高地址错位两个16位字的模式。这比“某一个物理Flash位随机损坏”更像局部数据流/地址对应异常；需优先核查烧录数据准备、传输缓冲、写入地址及校验、读取导出链路。尚不能仅凭导出文件确定是哪一环节。
4. 用户已确认XINTF勘误方向排除、重新上下电不能恢复、重新烧录才能恢复。按此事实推进持久程序镜像/烧录与校验链路排查，不再将XINTF二次复位勘误作为本案当前解释。完整断电不恢复也不能单独证明首次烧录就错，重烧还可能改变Flash设置、未导出区域或其他状态。

## 差异如何影响程序

### ram：.cinit初始化的EtherCAT对象字典出错

ram在0x321FC8–0x32201D共45个不同字，.text与OUT一致。

OUT启动入口_c_int00=0x31ED94；反汇编0x31EDA8起读取.cinit并向目标RAM执行PREAD复制。按该程序启动格式解析：负长度对应32位目标地址，随后是指定字数的初始化数据。三份不同镜像的1221条初始化记录边界完全相同，异常均落在同一条记录的数据体，记录头未变化：

| 项目 | 值 |
|---|---|
| 初始化记录头地址 | 0x3211AC |
| 长度字段 | 0xEBED，即有符号-0x1413 |
| 目标RAM地址 | 0xD700 |
| OUT目标符号 | _ApplicationObjDic（.pardata） |
| Flash初始化数据起点 | 0x3211AF |
| 数据数量 | 0x1413个16位字 |

因此，若DAT反映实际且启动按该OUT执行，ram的Flash差异会复制到RAM **0xE519–0xE56E**（范围内不是每字都不同）。涉及对象索引0x2176、0x2177、0x2178、0x2179、0x2180所在的表项区域。

具体例子：好件0x321FC7/0x321FC8为`805D 0033`，组成指针0x33805D，OUT符号为_sEntryDesc0x2176；坏件同位置为`805D 8019`，不再指向该正常描述表。后续还有对象索引、名字地址、变量地址等数据错位。无需XINTF底层总线整体失效，也可能出现对象字典查找、SDO/上位机参数读取等局部功能异常；具体失败调用和对象仍须结合客户源码与运行验证。

复核时应在main入口、C初始化完成但应用尚未修改字典前观察相关RAM，而不是只比较任意一段RAM或仅比较主循环前全部已被应用重写的状态。

### ram2：代码段和对象字典均异常

- 0x3082AE–0x3083EF：315个字不同，属于.text。
- 0x322310–0x322423：136个字不同，属于上述_ApplicationObjDic的初始化数据，将映射到RAM **0xE861–0xE974**。涉及0x606E、0x606F、0x6070、0x6074、0x6078、0x607B、0x607C、0x607E、0x607F、0x6080、0x6081、0x6083、0x6084、0x6087、0x608F所在表项区域；不表示每项所有字段均损坏。

OUT在0x3082AE为`ED08`，反汇编为`SBF 8, NEQ`，下一条0x3082AF/0x3082B0为`761F 03C6`（MOVW DP,#0x3C6）。ram2同地址序列却为`ED0C 761F ED08 761F 03C6 ...`。这已影响指令与操作数对应，不能只描述为一个低字节bit2变化；具体是否执行该路径及如何失效需要运行跟踪。

### 三段一致的错位模式

逐字关系均已验证：

| 镜像 | 区间（含端点） | 关系 |
|---|---|---|
| ram | 0x321FCA–0x32201D | 坏件[A]=OUT[A-2]，84/84字 |
| ram2 | 0x3082B0–0x3083EF | 坏件[A]=OUT[A-2]，320/320字 |
| ram2 | 0x322312–0x322423 | 坏件[A]=OUT[A-2]，274/274字 |

区间后的内容恢复与OUT相同，文件长度也相同。这是局部序列错位，不是整个文件永久插入两个字。不能因此直接断言主机插入、Flash API地址错误或芯片内部故障；只是比单点物理bit故障更有针对性的定位线索。版本不同仍应核对实际生产OUT的哈希，但当前没有第二份OUT支持“坏件就是另一个合法版本”的说法。

## 旧排查与当前证据的关系

长截图的历史记录：335b版本/B1芯片，产线烧录后部分产品功能缺失，部分SCI失联或链路可建立但读数异常；现场剩一台异常件。该现场件可经XINTF/EtherCAT控制电机、电流转速读取正常，而上位机读取部分内部数据异常。当时记录XINTF寄存器相同、Flash镜像相同、main循环前RAM相同；XCLKOUT约74–76MHz。曾改XRS复位RC（约1ms增加到约3ms）、规范烧录与脱离仿真器流程、加入XINTF勘误复位措施，但记录最后明确根因未定位。

历史“相同”仅适用于当时样品、导出范围和读取条件；不能据此否定这次的具体文件差异。这次发现对象字典初始化数据异常，也不能反过来证明历史所有异常必然同源。最新用户事实优先：XINTF勘误方向已排除、重新上下电无效、仅重新烧录恢复。

## 现场补充确认与排查收敛（2026-10-26）

用户进一步确认：坏件暂停CPU重复导出、Memory Browser查看时，错位稳定存在；同一份OUT重新烧录后立即恢复；现场发生频度约为几千台中一两台。这是用户报告的现场现象，不等于已取得首次烧录后分阶段回读和完整独立校验日志，也不转换成经过统计验证的失效率。

因此，不再将重复导出或等待同一板重烧后立即复现作为当前主任务。现有证据更支持稳定存在、可通过重新编程恢复的Flash镜像异常；零散瞬态启动状态与偶发单次导出异常的解释力下降。局部两字错位仍优先提示烧录数据准备/传输缓冲/目标地址对应及验证覆盖问题，不能仅凭低发生率或重烧恢复判定具体环节，更不能据此排除器件或烧录供电/时序问题。目标侧缓冲区错误若参与了写入和同源校验，可能同时被漏检，需与原始OUT进行独立回读比对。

下一项关键资料是产线实际烧录方式（CCS/JTAG、离线烧录器或BOOT升级）、工具/算法版本、是否执行独立全段Verify、失败判据及日志。优先将与固定生产OUT逐地址核对的独立回读校验加入烧录后、产品功能测试前，并保存工具/工位/仿真器/芯片批次及镜像哈希。若将来首次烧录后即捕获错位，定位烧录链路；若有完整正确回读记录而随后才发生错位，转查运行期擦写或其他后续因素。

### 产线方式及运行期方向的进一步收敛

用户确认产线通过CCS/JTAG进入Debug模式烧写；用户团队讨论后认为不会误调用Flash API，当前排除运行期“插入两个数据造成后续错位”的解释。该项为用户提供的工程排查结论，本次未取得客户完整源码验证所有运行期擦写调用。

Flash按固定地址存储，不具备在某地址插入两个字并自动移动后续内容的操作；这一点同样适用于CCS/JTAG烧录。普通覆盖/擦除不能自行产生整段有序移位，但如果某条写入路径拿到的源数据或地址对应已错，擦除后再编程仍能在固定地址形成“看起来插入”的结果。因此，不能仅凭没有硬件插入命令作逻辑上的完全排除；结合用户团队已排查无运行期Flash API误用，本案将其降为后备方向，不继续作为主任务。

当前优先核查CCS装载链路：生产OUT哈希及实际加载文件、目标Flash算法/版本、JTAG及目标RAM暂存数据、分块写入源数据与目标地址对应、校验范围和依据。未证实错位由特定缓冲区、分块边界或仿真器造成。两个字的错位仅是模式线索，不足以确定具体传输或编程粒度。

CCS进入Debug后可能自动运行到main；该行为已执行C初始化，不能等同“刚写完且未运行”。后续若采集时间证据，应明确自动运行设置及实际暂停时点；当前不要求等待低概率故障复现。优先确认生产下载是否确实执行独立完整校验，具备条件时将读取实际Flash并与原始OUT比较的验证设置为放行条件，而不只检查下载完成提示。

### CCS快速校验的明确覆盖限制

用户确认产线配置为“快速校验”。本机CCS12.7随附用户手册的Program/Memory Load Options → Verification Options明确说明：Full读取整个已装载程序；Fast仅读回已装载内容的最前和最后20个word。此处指Debugger通用装载校验选项Fast verification，不与其他芯片Flash插件的Fast Verify选项混淆，也不将其误说成全量CRC或累加和校验。客户CCS版本未另行提供，具体选项如有差异须按客户版本核对。

本次差异落在.text/.cinit内部，快速校验通过不能证明中间内容正确。这为“程序内容不同却未被CCS装载快速校验拦截”提供明确的漏检机制，但不是造成错位的写入根因，也不等于已证实Flash算法没有另外进行内部Verify。

建议生产配置改为Full verification，并用仍保留坏内容的板卡执行Verify Program对照同一369.out：只校验，不执行Load/Reload，不重烧。随附GEL_VerifyProgram文档明确其等同完整装载校验，跳过实际装载、只比较现有目标内存与程序文件。尽量在Flash装载地址及坏件现场状态下核验，关注已知差异地址的报错，不让自动加载覆盖证据。之后再追查首次写入为何出现两字错位。

### 产线CCS6 + XDS100v2：写入根因继续定位

用户补充产线为CCS6、XDS100v2，随机出现；完整CCS补丁版本、TI Emulators版本、Flash插件/算法及TCLK尚未取得。不能因为版本较旧就宣称已确认驱动BUG。完整Verify是拦截措施，不是消除两字错位原因的措施。

TI官方SPRABV4A第2页Programming Fundamentals说明，C2000的CCS/JTAG Flash操作也通过加载算法到RAM、由CPU执行完成。这是理解烧录路径的TI C2000基线；进芯335B1现场具体采用哪份适配算法，还须核对安装包、目标配置及日志，不能仅看CCS6版本或客户OUT内有没有Flash API调用。客户应用运行期未调用Flash API，不排除烧录工具内部算法/数据处理环节的问题。

以当前两字局部错位模式，优先调查源数据/暂存缓冲/写地址对应，尚不支持认定单个Flash物理bit随机失效。真正定位写入环节的判据应是：若烧录算法调用前的源缓冲数据已错，则沿PC加载器/JTAG/目标RAM暂存查；若源数据、地址、长度均正确而Flash读回错误，则沿Flash算法适配、烧录时钟/供电及器件侧查。这需要原厂或工具方对实际烧录插件/内核提供日志或可观测手段，不能单凭当前OUT逆向得到烧录插件内部缓冲内容。

可先在备板进行不擦写Flash的JTAG→已知空闲RAM大块数据写入/完整回读压力测试，比较固定数据与地址标记，观察有无同型两字错位；若复现，可将线索定位到非Flash编程路径，若不复现则不能排除烧录特定路径。后续对照保持生产OUT原文件不重编译，每组只改变一个因素：同一XDS100v2对比经进芯确认支持的另一CCS/驱动环境；同一软件环境对比另一受支持仿真器；另组再调整可配置的TCLK/线缆/工装。固定原始基线并保留失败样本及批次数，短期未出现不足以宣称解决低概率故障。不要将测试用RAM覆盖到仍需保全的坏件程序上下文。

另查到TI E2E案例“Memory Browser has an address offset of 2 words”：C28346 + CCS5.5 + Signum JTAGjet，用户报告Watch与Memory Browser值对应不同，改用XDS驱动连接项后恢复。该案例不同于本案XDS100v2，不能作为本案根因或已知BUG证明；它仅说明同一驱动反复读出稳定偏移在原理上仍可能是访问链路问题。若仍有未重烧坏件，值得用独立仿真器/驱动只连接、不Load复核一次；这与重复原有同一路径读取的测试不同。

### UniFlash校验路径核查（本机8.3.0及官方v4+指南）

不能笼统称“UniFlash默认就是完整校验”。本机8.3.0的`uniflash/public/uglify.js`中，GUI Load操作调用`symbols.loadProgramOnly`，独立Verify调用`symbols.verifyProgram`；操作按钮模板`ds/program_actions.html`通过主按钮旁下拉菜单呈现额外操作，代码中主操作Load、额外操作Verify。因此界面没有CCS相同的Fast/Full切换项，不代表没有独立完整程序校验入口。Verify Image按所选OUT可装载内容对照目标内存，不要求OUT未定义的空白区域也全部等于特定值。

此外，本机标准TI F28335插件的`TMS320F28335_FlashProperties.xml`第125–136行，FlashOperations默认值是`Erase, Program, Verify`，包含算法层Verify；这是TI F28335标准插件配置，不直接证明客户进芯335适配插件的实际行为。不能把Load成功直接等同独立的主机OUT全段校验，也不能因为调用名loadProgramOnly便声称底层Flash算法完全不校验。

生产显式流程：GUI先Load Image再通过旁边下拉执行Verify Image，确认Program verification successful；或独立命令行包使用`-f -v`，分别显式要求烧写与校验，保存日志及返回值。官方Quick Start的CLI示例明确包含`-e -f -v`，-v为烧录后校验。这里只核查文档与本地实现，未连接客户板执行UniFlash验证。

### 客户小型FFC软排线及转接板假设

用户补充JTAG经小型软排线连接，照片可见DSP/CPLD烧录转接板、IDC排线以及两条白色带蓝色补强片的FFC软排线。照片不能确定线长、针脚/地线分配、连接器接触质量、两路是否同时驱动或信号波形；不凭外观认定线缆不合格。

该转接链路值得优先作单变量替换试验。细间距FFC本身可以可靠传输JTAG，关键是TCK与数据信号的回流路径、串扰/反射、接头接触和分支负载。数据量增加意味着更多传输机会，可能暴露低概率错误，并不等同“大数据量会自动导致线缆错误”。普通位采样错误不能单独充分解释已观察的局部连续两字错位，不能把照片直接作为写入根因证据。

建议固定同一CCS6/驱动、XDS100v2、原始OUT、板卡和供电，仅对比原转接FFC链路与短且已验证可靠的连接链路；所有样本都作独立完整Verify，记录首次失败地址及工位/线缆编号。若TCLK可调，可另组单独降频；换线与降频同时做不能区分原因。先在芯片端使用短地弹簧测TCK过冲、振铃和阈值重复穿越，再核对TMS/TDI/TDO及供电/复位；具体整改电阻或端接须根据拓扑和波形决定，不凭照片指定数值。短期零失败不足以证明解决几千台一两台的低频问题。

## 初始排查路径及判据（保留追溯）

1. **先保留一个坏件，不擦不烧，复读两次。** CPU暂停，在Memory Browser定点查看0x321FC7起、0x3082AE起、0x322310起，并重复导出；必要时换读取工具/仿真器验证。Flash时序/访问配置、读取工具和导出链路仍可能影响读值，不能仅由导出文件宣布物理存储已变。如果复读文件不稳定，先定位读取链路；若值稳定且不同方式一致，再加强实际镜像异常的判断。
2. **烧录前固定唯一基准及生产过程。** 保存实际生产OUT的SHA256、烧录软件/仿真器版本、设置和日志。确认比较的是同一版本；完整验证应覆盖所有已装载段，不只0x300000–0x337FFF，也不只进行下载后运行。
3. **在重烧同一个坏件时建立时间闭环。** 依次记录：烧录前坏镜像→同一OUT烧录并明确校验→运行客户程序前立即独立回读→运行后回读→断电再上电回读。若工具不能在运行前暂停，使用具备Program+Verify及不自动运行能力的流程，并检查GEL/on-load脚本自动动作。烧后立即错，定位下载/数据缓冲/地址推进/写入及校验；烧后正确、运行后才错，转查运行期擦写、升级入口和供电等。烧后一直正确但故障再次出现，则说明当前Flash差异未必解释全部现象。
4. **对“校验通过”保留独立证据。** 区分写API成功、依同一个源缓冲区做局部Verify、与原始OUT作全段独立回读三件事。若源缓冲区在写前已错，同一错误缓冲区参与Verify仍可能通过；这是待查机制，不是本次已证明的原因。

目前最有力的直接线索是“OUT不符，且损坏范围落在EtherCAT应用字典初始化数据与程序代码”。差异何时形成、由哪个环节造成，尚需上述时间闭环确认，不据此先判芯片Flash物理质量或宣称首次烧录必然失败。
